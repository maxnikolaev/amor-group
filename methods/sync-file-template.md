# SYNC-файл проекта — стандарт

> Каждый проект (кейс) в `cases/` содержит файл `sync.md` в корне.
> Это — единый источник правды по текущему состоянию проекта.

---

## Назначение

`sync.md` отвечает на четыре вопроса:

1. **Где мы сейчас?** (статус)
2. **Что сделано?** (факты)
3. **На чём застряли?** (блокеры)
4. **Что дальше?** (следующие шаги)

---

## Структура

```markdown
# SYNC — [Название проекта]

> Дата последнего обновления: YYYY-MM-DD

## 📋 Статус: [ФАЗА]

Краткое описание сути проекта (1–3 строки).

## ✅ Что есть / сделано
Таблица: Что | Детали

## ❌ Чего не хватает / блокеры
Таблица: # | Блокер | Влияние | Что нужно
Приоритет: 🔴 критично → 🟡 важно → ⚪ потом

## 🔜 Следующие шаги (приоритет)
Нумерованный список с конкретными действиями

## 💰 Ключевые цифры
Таблица: Параметр | Значение | Источник

## 📝 История обновлений
- YYYY-MM-DD: что изменилось
```

---

## Правила ведения

1. **Обновлять при каждом изменении** статуса, блокеров, шагов
2. **Дата** — вверху, обновляется при каждом изменении
3. **Блокеры** — честно и конкретно, с указанием что блокирует и что нужно для разблокировки
4. **Следующие шаги** — actionable (конкретные действия, а не «подумать»)
5. **Цифры** — с источником (документ, расчёт, оценка)
6. **История** — короткая строка с датой и сутью изменения
7. **Один файл на проект** — не плодить дубликаты

## Исследования (research)

Каждый кейс содержит директорию для исследований:

```
cases/[кейс]/материалы/research/
├── YYYY-MM-DD_тема-исследования.md    # конкретное исследование
├── YYYY-MM-DD_тема-исследования.md
└── ...
```

### Правила

1. **Один файл = одно исследование** с датой в имени
2. **Полный отчёт** сохраняется в `research/`, не в чате
3. **В чат** — только краткий вывод (executive summary)
4. **Формат Markdown**, структурированный, с источниками
5. **Содержит:** контекст исследования, методология, находки, выводы, источники
6. **Обновляется** при появлении новых данных (с указанием даты в истории)
7. **Связан с sync.md** — если исследование закрывает блокер или меняет статус, обновляется и sync.md

### Триггеры для исследования

- Появление нового блокера, требующего анализа рынка/нормативов/технологий
- Запрос от Макса или Александра на анализ чего-либо
- Необходимость сравнения с конкурентами/аналогами
- Оценка стоимости/сроков/рисков перед принятием решения

## Логи и вехи (log)

Каждый кейс содержит директорию для логов — полноценных разборов этапных выводов, корректировок модели, инцидентов.

```
cases/[кейс]/log/
├── YYYY-MM-DD_краткое-название.md    # веха / инцидент / корректировка
├── YYYY-MM-DD_краткое-название.md
└── ...
```

### Что писать в log

- **Этапные выводы** — по итогам анализа, исследования, встречи
- **Корректировки** — изменения в финмодели, стратегии, допущениях (что было → что стало → почему)
- **Инциденты** — обнаруженные ошибки, расхождения, блокеры с полным разбором причин

### Правила

1. **Один файл = одно событие** с датой и кратким названием в имени
2. **Полный разбор** сохраняется в `log/`, не в чате и не в sync.md
3. **В sync.md** — только ссылка на веху в секции «История обновлений» или в соответствующем блоке
4. **Формат Markdown**: контекст → суть → разбор (с цифрами/таблицами) → вывод → что меняет в проекте
5. **Связь с sync.md:** при создании вехи — обновить sync.md (добавить ссылку, обновить статус/блокеры при необходимости)
6. **Связь с research/:** если лог ссылается на исследование — указать путь к файлу

### Отличие от research/

| | `research/` | `log/` |
|---|-------------|--------|
| **Что** | Внешние исследования, рыночные данные, аналоги | Внутренние события проекта: выводы, корректировки, инциденты |
| **Триггер** | Нужно узнать что-то извне | Произошло что-то внутри проекта |
| **Пример** | «Экономика малых поселков 2026» | «CAPEX занижен в 2 раза — разбор» |

## Автоматизация

- Файл `sync.md` — основа для канбан-доски (будущее)
- Статус / блокеры / шаги → колонки доски
- Hermes обновляет файл при работе с проектом
- При `git pull` — актуальное состояние доступно всем участникам
- Ресерчи накапливаются в `материалы/research/` и доступны для реиспользования
- Вехи накапливаются в `log/` — полный аудиторский след проекта
